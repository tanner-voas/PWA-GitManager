# PWA-GitManager v0.1.25

A mobile-first GitHub workspace manager for AppLauncher and a standalone recovery URL. GitHub is the source of truth; the iPhone never needs a local Git clone. The implementation is split into this repository (browser app + Cloudflare API) and **PWA-GitRunner**, a separate **private** repository that runs trusted GitHub Actions jobs. Install the same private GitHub App on all repositories you want to manage, including both of these. New installations/repositories are discovered from the installation API, not AppLauncher's application list.

## Usage

* **Repositories:** see live main commits, declared versions, revision tags and AppLauncher production. Select a repository for commits, tags, branches, directory/file contents, Gitlinks, open PRs and Actions runs. Verify workspace compares pins with installed upstream mains; older pins may be intentional. Source ZIPs can be prepared for native file sharing. Export workspace creates a private Actions artifact with complete Git histories, tags and pins; choose lightweight (uninitialized submodules), recursive or Git bundles. Use Activity → Share workspace archive to share the original `workspace.tar.gz` directly. Extract once using a tar-capable extractor (e.g. `tar -xzf git-workspace-<id>.tar.gz` in an empty directory). The original GitHub Actions artifact remains an explicit fallback. In-app preparation is bounded to 256 MiB; for larger exports select fewer repositories. Exports are snapshots taken sequentially, not an atomic snapshot of independent repositories; `WORKSPACE.json` records exact commits, branches, tags and Gitlinks.
* **Updates:** choose an individual .patch, .diff, .bundle, or a ZIP with `manifest.json`. Review the ordered version summary; edit the manifest in Advanced if needed. Standalone patch/diff/bundle uploads ask for their repository only when necessary. A separate scrollable review dialog confirms the exact draft, not publication. Legacy ZIP file names matching `Repo_vA.B.C.patch` are recognized, but order and dependency pin rules must be reviewed explicitly. File editor/upload/delete and revert controls create the same kind of update draft. Never upload secrets as repository files.
* **Settings:** sign in with the existing Google Drive account, then enter the separate administrator unlock phrase. The server validates the password once in a POST body and returns a 4-hour HttpOnly, Secure, SameSite=Strict cookie. Privileged operations require that cookie, including export. It does not replace Google authentication. Existing short-lived cookies retain their original expiry; unlock again to obtain a four-hour session. Privileged actions visibly link to Settings when locked. Foreground service operations display an explicit loading indicator.
* **Activity:** patch jobs require draft review and explicit start; exports may start directly. Direct mode prepares, validates, and publishes the exact validated commit; PR mode prepares a branch and opens a PR for manual review/merge on GitHub, then pauses until you click Recover/resume. Dry-run validates without write credentials; dry-run dependency chains with unpublished pins are deliberately unsupported. Read-only exports never push. The runner continues independently of the phone after approval. Open Runner logs for actual Actions diagnostics or share the job JSON for another ChatGPT session. Run tag sync and AppLauncher reconciliation from the Actions view when necessary.

## Version enforcement (mandatory)

Every commit published by the manager is exactly one non-merge commit on the observed remote main, with root `package.json.version` or `VERSION` increasing by exactly one allowed step. For A.B.C, allowed successors are A.B.(C+1), A.(B+1).0, (A+1).0.0. No unchanged versions, revision suffixes, skipped versions or decreases. The manifest is checked, and the real candidate Git tree is checked again by the independent publisher; changing a manifest alone cannot bypass this. Known runtime declarations are checked by trusted policy. File-only changes and reverts automatically bump the declared version; Ciyan file-only changes add an identity backup migration. Use a proper patch for schema-changing code. Existing automatic dependency commits are exempt because they are produced by existing workflows, not this manager. Existing reusable tagging workflows remain authoritative for `vA.B.C` and `.rN`. Manager never force-pushes main or production and does not create release tags directly. PR creation pushes one versioned candidate; the actual GitHub merge is a separate human action. Prefer direct mode to enforce the gate immediately at publication. Recheck the base version before merging externally; if it changed, cancel the old PR and prepare a new patch.

## Dependency and race model

One durable coordinator serializes jobs across the entire installation, with a persistent active-job pointer, unique attempt IDs, run claims and immutable publication records. Each job applies repositories in the explicit ordered manifest. The runner clones fresh main, accepts a declared older base only if it is an ancestor, checks the version, applies `git am -3` (or another declared operation), resolves explicit Gitlinks using the actual already-published dependency commits, initializes exact recursive pins, then tests an isolated copy. Before any write, the trusted publisher fetches main again and independently verifies candidate parent, tree, version and explicit dependency heads. Normal fast-forward pushes reject a concurrent update even between the last check and the push. Race results retry up to three times, creating a completely new candidate and re-running tests. Stale callbacks are rejected. A version advancement by somebody else stops the job instead of silently bumping or overwriting.

Before each update and after the last publication, the runner follows the transitive automation graph in `PWA-GitRunner/runner/policies.json`. It waits for active Actions to finish, successful expected workflows for the exact published commit, the published revision tag, downstream workflow evidence, required Gitlinks and matching AppLauncher main/production. A 30-second stable-head quiet period follows. The barrier applies even when a downstream repository is next in the package. No phone connection is needed: the Worker dispatches the next attempt automatically. Progress is stored durably and displayed in Activity. A nine-minute observation timeout schedules up to two additional observation attempts using a Durable Object alarm; if still not settled the job pauses for inspection. Missing completion callbacks are detected by a watchdog; uncertain writes are never automatically repeated. Reconciliation failures are visible and can be retried after correction; a later patch cannot bypass a failed barrier.

At preparation **and** immediately before publication, every Gitlink in the candidate is matched against its committed `.gitmodules` URL and fetched by its exact SHA into a new empty bare Git repository, recursively. The same URL+commit can be reused within that one verification; no preexisting local objects or successful local build can stand in for remote retrieval. Missing/unpublished commits, malformed Gitlinks, or inaccessible nested submodules block publication. Declared dynamic pins are excluded from patch application and inserted using the actual published upstream SHA (or its current reachable descendant), never a locally generated SHA. A remote change during validation causes a new candidate and retest. The launcher-specific invariants and expected push workflows are in trusted policy; update that file when introducing new cross-repo dispatches. GitHub does not expose a complete causal graph for arbitrary workflows, so unknown cross-repository automation needs explicit policy, and Cloudflare build completion is not polled by the runner. The final boundary is a fresh exact parent and a fast-forward-only push, not the quiet period. Already published upstream commits are retained if downstream fails; do not blindly reapply a partially published package.

## AppLauncher update notifications

Every push to `main` triggers `.github/workflows/notify-app-launcher.yml`, which sends the `gitmanager-updated` repository dispatch. Configure the repository Actions secret `APP_LAUNCHER_DISPATCH_TOKEN` with AppLauncher Contents write access. The workflow can also be triggered manually. The existing backend self-update dispatch and scheduled launcher reconciliation remain fallback mechanisms; launcher concurrency serializes redundant notifications.

## Further documentation

* `SETUP.md`: GitHub App, Cloudflare, R2, runner secrets, standalone and launcher setup.
* `PATCH_PROTOCOL.md`: manifest schema, examples, HTTP interface and handoff rules for future ChatGPT sessions.
* `SECURITY.md`: trust boundary, recovery, limits and operational precautions.

Build: `python3 package.py` (emits `dist/gitmanager` and `dist/standalone`). Test: `npm test`. No npm install is required. Runner tests: `python3 -m unittest discover -s tests` in PWA-GitRunner. The initial implementation is local-test validated, not yet live-deployment validated. Perform a dry run before first publication. General branch deletion/creation, repository creation, graphical conflict resolution, large-file multipart uploads, and in-app PR merge are not implemented. Repositories without canonical versions can be browsed/exported but cannot be mutated until versioning is established. Unknown test policies fail closed unless a valid npm test script exists. Submodule execution currently supports same-owner HTTPS GitHub repositories only. The manager never claims to validate a repository with no test policy; Chronicle's explicit policy is only a whitespace/diff check, since it has no application code yet.

## Telemetry foundation
Settings contains explicit administrator-gated enrollment and archive status. The server-only Profiles service binding returns a narrowly scoped append capability stored privately in the job coordinator; there is no browser token or public append route. This release captures only Drive events. Collector adapters, reporting and share actions are later telemetry phases. Requires deployed PWA-GoogleDrive v0.1.14. Older Profiles Workers remain compatible with ordinary jobs.

### v0.1.11 combined telemetry reliability and R2 observations

This release supersedes the separately prepared v0.1.11 UI package. In Settings, **Test GitHub collection now** makes a bounded, administrator-authorized foreground diagnostic of PWA-GitRunner using the existing read-only installation access. It collects up to ten recent run observations, one completed attempt's job/step metadata and one run-level artifact listing (at most 30 entries); it submits stable records directly to the Drive archive service, bypassing the scheduled collector and its forwarding queue, then requests a flush where possible. It reports per-stage outcomes, newly accepted/duplicate/rejected counts, safe HTTP status and receipt state; append acknowledgment is not proof that those specific records were written to Drive. Use **Share telemetry status** to share the current archive/collector counters and the last direct test from this browser session, even if it fails. A diagnostic may be repeated after cooldown; no runner is dispatched. Do not disable/re-enable for testing. If the stored append authority is missing or revoked, **Repair collector authorization** refreshes it without disabling the archive; renewal of the same trusted enrollment preserves pending outbox records. Actual revocation/new enrollment still separates queues.

GitManager now instruments its own R2 package bucket get/put/delete attempts: counts, outcome, elapsed milliseconds, observed read size or attempted write size, and job correlation. These events are application-observed, not official R2 billing totals or storage inventory. GitHub artifact observations are bounded listing snapshots, not storage-time or billable usage, and are run-scoped rather than attempt-scoped. Raw logs, provider usage, background collection acceptance and broader archive extraction remain pending. No new cloud credentials or bindings.
