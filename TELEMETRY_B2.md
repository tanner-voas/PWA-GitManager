# Telemetry B2 — Independent GitHub Actions discovery

GitManager 0.1.8. Existing A2/B1 enrollment and outbox stay intact. The first authorized Settings status visit initializes a separate `workspace-workflow-poller-b2` instance of the existing JobCoordinator binding. Its alarm and state are independent of the publication lock and B1 forwarding alarm. Initial scan is due in one minute; subsequent successful scans every five minutes, one repository per tick. Collector refreshes installation repository list at the start of each round. PWA-GitRunner is first; other known schema repositories are sorted. Works after the app closes. No new Actions jobs, credentials, or paid services. Disabling the archive stops the poller; an invalid/revoked archive authority stops it once detected. It reads the current authority each tick and resets observations when authority changes.

- A bounded first-page scan of the latest 20 workflow runs per repo, considering runs updated in the last 24 hours. This is a rolling lookback, not a guaranteed complete GitHub history. Old reruns outside the latest page and busy repos may be missed. Installation discovery is bounded to 100 entries, and only the ten schema-known repositories are collected. Limits are reported, not silent success. Repository discovery and workflow snapshots do not change branches or tags.
- Completed runs queue an attempt-specific job metadata lookup; at most one per tick. A 60-run bounded pending detail queue prioritizes failures, then newer runs; max 12 jobs and 30 detail events per run, first 20 jobs from API. Truncation is reported in status and a coverage event for truncated detail batches. If a detail lookup returns 404, mark unavailable and continue. Bounded two-day dedup caches (400 run/detail keys each) and deterministic B2 event IDs. Overlap with B1 observations is deduplicated within the existing outbox observation window; no claim of global exact-once after cache eviction.
- Each workflow run contains provider run ID/attempt, repo, SHA, outcome and observed timing. Each job or step uses the same run correlation; `correlation.requestId` is an opaque SHA-256-derived job key (not a request from the browser); job `metrics.count` is number of steps, step `metrics.count` is the step ordinal. `durationMs` is the elapsed provider interval, not billable minutes. Job/step names, commands, log text, URLs, tokens, artifacts and other unstructured data are intentionally not collected in this release. Raw sanitized logs, billing/usage accounting, richer explicit IDs and artifact metadata are future TEL-04/TEL-11 slices. Never sum workflow, job and step durations as independent billed usage.
- Each tick attempts at most one token mint, one installation list (only per round), one run list, and one detail lookup. No token persisted. Normal ten-repo cycle approximately 50 minutes; max normal 288 ticks/day, up to four attempted API calls/tick, typically fewer. API attempts counter is local collector overhead, not account-wide usage. No extra CI runner minutes. Backoff for provider error (10 min to 6h, respects longer Retry-After/rate reset), manual does not bypass. Archive backpressure skips polling when forwarding queue >32 or queued forwarding is failing; enqueue has atomic capacity guard to reserve space for job telemetry. No new storage binding. Coverage may be partial after backlog/retention limits. Free Workers CPU/runtime performance is not verified on actual deployment.
- Settings shows last and next scan, counters, backpressure, coverage limits and safe error categories. **Collect next repository now** requests one immediate alarm, at most once/minute, requires administrator access. **Refresh status** observes progress. **Upload pending now** remains separate and forwards one bounded producer batch plus one archive batch. No changes to global workspace job behavior, archive retention or other UI tasks.

## Live test
1. Apply update and verify GitManager 0.1.8, Workers deployed and existing unified archive still enabled. Do not disable/re-enable solely for testing. Open Settings once to initialize the new poller. Verify `GitHub Actions collector` scheduled.
2. Unlock admin and tap Collect next repository now. After the alarm runs, refresh status. First scan should be PWA-GitRunner. Repository scans should be >=1, detailed runs >=1 if a completed run is present. Check last error and coverage hits. There is no need to open any repo's Runs page or start a new job.
3. Close the app for 6 minutes. Reopen Settings and check that automatic repository scan count advanced. Repeat if the provider/backpressure delayed it.
4. Upload pending now (one batch, one-minute cooldown); repeat as needed or allow automatic archive flush. Share new Drive chunks plus screenshot of status. Expect `github-actions` operations `workflow`, `job`, `step`, correlated with repo/run IDs and outcome; compare a recent known export run to GitHub. No secrets, names or raw execution log text expected.
5. If no events, check collector status/error and latest pwa-git-api logs. Do not disable existing archive to force a poll. Actual hosted alarm, permissions, rate behavior and coverage still require live testing.
