## TEL-04 — checkpoint and catch-up

Explicit verified shutdown keeps the workflow discovery cursor, pending detail requests, dedup keys, counters and provider retry deadline in the existing poller DO, and stops its alarm. No capability is stored with the checkpoint. A new enrollment rotates capability generation normally; resume compares SHA-256 of the trusted server-issued account subject and authorization epoch (legacy null epoch is distinct from a revoked/reconnected UUID epoch). This comparison is continuity only; actual appends still require a valid signed capability with the current generation and epoch. The explicit stop verifies the previous enrollment or owner hash. The disabled status does not reveal repository/run identifiers or counters from a paused checkpoint. Different account/epoch, missing authority during active polling, or revoked active producer state clears old discovery state. Checkpoints older than two days are discarded on next disabled status or resume; pending detail expiry remains two days, dedup retention and size bounds remain. No timer while paused, so an unused expired checkpoint may remain physically stored until the next access. R6 already discarded old pending requests; cannot recover those from R7. Manual scans cannot bypass backoff. Existing shutdown drain, archive authorization and retention are unchanged.

At least 48 eligible details on alternate automatic alarm ticks: skip repository discovery and process up to two details when producer pending <=16, otherwise one. Normal ticks scan at most one repo and one detail; manual scans still use normal behavior. At most two workflow/detail provider requests per catch-up tick (installation inventory/token overhead as before); no new fixed API frequency. At two-minute intervals, sustained eligible backlog may process up to 45 details/hour vs 30 in R6, while repository discovery slows to every other tick. Queue admission and backoff still govern. Limit is theoretical, not guaranteed; oldest detail requests expire, detail rows still capped at 30, workflow list at 20 and queue at 160. State remains capped at 110 kB. New diagnostics: resumed checkpoint count, detail-only catch-up ticks. No raw GitHub logs or pagination expansion.

## TEL-16 — proposed contract, not a new active mode selector

- Developer archive: current account-wide unified event archive, enabled only by an authorized administrator; event-level operational metadata, native provider observations when available, and existing bounded retention. Disabled means this archive is off, not that Standard aggregation is implemented. Existing legacy Drive network telemetry continues under its existing rules.
- Standard: future low-volume counters per app/profile and installation/device writer, for attributable usage (e.g. submitted translation characters, synthesis characters, requests). Persist compact cumulative bucket snapshots with ordinary backups, with source, unit, period, owner scope, writer ID, stable bucket identity, revision, measured/estimated/unavailable, and last observation time. Account/provider-wide costs or quota usage must be separate account-level aggregates, not copied into each profile as additive usage. Local counters cannot assert actual provider billing. Merge by writer+bucket identity using monotonic revision; conflict forks are not additive copies. Retain bounded day buckets; proposed 30-day detailed daily rollup with longer monthly rollups subject to approval. No new backup format in R7.
- Collection and aggregation must use a canonical operation identity at the source. In Developer, the same usage counter may continue to be updated once and event detail separately archived; do not sum event-derived usage with the corresponding counter. Provider totals are independent reconciliation observations, not additional requests. Cache hits must not increment paid request/character totals unless provider usage says otherwise; distinguish reserved/attempted/confirmed. Counter revisions rather than increments on retry. Different writers may only contribute disjoint attributable operations; otherwise mark overlap unknown.
- Transition: serialize and drain accepted buffers before Developer -> Standard/off; verification failure leaves transition retryable, no silent discard. Standard -> Developer starts a new event coverage period, preserves historical aggregates and verified archive; optional provider retrospective records labeled by occurrence/observation. Profile switching never changes account-wide archive ownership; reauthorization/revoke invalidates upload generation and epoch; historical Drive data remains unless user explicitly deletes it. Standard -> Developer and reverse mode behavior requires approved backup ownership schema and real source accounting tests before activation. No automatic sharing, new permissions, paid services or fabricated quota coverage.
